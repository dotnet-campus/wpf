# wpfgfx C#/.NET Native AOT 迁移章程

> 状态：强制执行  
> 适用范围：`WpfGfxShape` 下的全部调查、设计、实现、测试与交接工作  
> 目标源码：`src/Microsoft.DotNet.Wpf/src/WpfGfx` 及其直接依赖、生成协议和托管调用方  
> 新代码根目录：`WpfGfxShape/Code`  
> 文档根目录：`WpfGfxShape/Docs`

## 1. 目标

将现有 WPF `wpfgfx` 原生图形层逐步迁移为 C#/.NET 代码，并使用 .NET 10 Native AOT 生成原生库，继续导出与现有调用方兼容的 C ABI。迁移后的库应尽可能在不修改或仅最小修改现有 WPF 托管调用方的情况下替换原 `wpfgfx`。

本项目首先追求可证明的语义等价、ABI 兼容和完整流程可运行；代码风格现代化、抽象优化与性能改进均属于等价迁移完成后的独立阶段。

## 2. 约束优先级

发生冲突时，必须严格按以下顺序决策：

1. **正确性与可验证的行为等价。**
2. **现有 C ABI、二进制布局、调用约定和生命周期兼容。**
3. **逐文件、可审计、可回退的迁移过程。**
4. **可构建、可测试、可跨会话继续。**
5. 迁移速度。
6. 代码简洁度、现代化程度、抽象质量和性能优化。

后续任何设计若以“更优雅”“更现代”“更高性能”为理由损害前四项，必须拒绝。

## 3. 最强实现约束：逐文件近似直译，禁止提前重构

以下规则是本项目的最高实现原则。它服务于第 2 节中优先级更高的“正确性/可验证行为等价”和“ABI/生命周期兼容”，不得被解释为可以机械照抄已确认错误或绕过验证：

- 初次迁移必须以原生源码为基准，按文件逐个迁移。
- C# 文件应保留与原 C/C++ 文件清晰可追溯的对应关系；原则上一个原生实现文件对应一个主要 C# 实现文件。
- 尽量保留原类型名、函数名、字段名、常量名、分支结构、调用顺序、错误处理顺序、锁顺序、引用计数语义和资源释放顺序。
- 原生目录虽最终合并到一个 .NET 生产项目中，但 C# 目录层次应尽量镜像 `WpfGfx/common`、`WpfGfx/core`、`WpfGfx/shared` 等原始边界。
- 单项目仅表示构建和发布边界统一，**不表示允许在迁移期合并原有模块职责或重新设计架构**。
- 每迁移一个文件，都必须记录原始路径、新路径、直接依赖、未解析依赖、测试状态和与原实现的已知差异。
- 一次变更只处理一个可说明的迁移单元；不得顺带清理附近代码。
- 每个生产文件在编码前必须已有 Ledger 行、原路径到 C# 路径映射和预先定义的验证证据；没有台账和测试定义时不得开始翻译。

在完整等价迁移达到既定验收门槛之前，禁止：

- 重构、抽象重组、职责合并或拆分；
- 为“更符合 C# 习惯”而改变算法或控制流；
- 提前应用性能优化、缓存策略变化或并发模型变化；
- 删除看似无用但尚未证明不可达的分支、状态、兼容逻辑或错误码；
- 将多个原生文件任意揉合为一个无法追溯的 C# 实现；
- 在没有差分测试证据时用第三方高层封装替换底层语义；
- 以测试困难为理由跳过生命周期、失败路径、设备丢失、线程和资源释放逻辑。

若 C# 或 Native AOT 无法逐字表达原语义，应采用最接近的低层表达，并在迁移台账中记录偏差、原因、风险和验证方法；不得静默改变语义。

## 4. ABI 与导出兼容原则

- 现有导出函数集合、导出名、参数顺序、返回值、调用约定和结构体布局是外部契约。
- 所有托管 `DllImport`/P/Invoke 声明、原生头文件、`.def` 文件、生成导出、链接器配置和实际二进制导出都属于 ABI 事实来源。
- 不得仅凭单一文件推断完整导出面。
- Native AOT 导出入口必须是薄边界：完成参数校验、ABI 类型转换、异常封锁和对内部等价实现的调用。
- 任何托管异常都不得跨越 C ABI 边界；异常到 HRESULT/错误码的映射必须与原实现一致或被明确记录和验证。
- COM 指针、引用计数、句柄所有权、回调函数指针、字符串编码、布尔值宽度、枚举基础类型、对齐和打包规则必须逐项确认。
- 在替换现有库前，必须拥有自动化 ABI 清单和可重复的兼容性验证。

## 5. 项目形态原则

初始方案如下，除非后续调查提供反证并形成书面决策，否则不得擅自改变：

- 在 `WpfGfxShape/Code` 下创建完全独立的 .NET 10 生产项目。
- 生产项目采用 Native AOT 原生库发布能力，并导出兼容 C 函数。
- 所有迁移后的 wpfgfx 生产逻辑置于同一个 .NET 项目中。
- 在同一根目录下创建独立测试项目；测试项目不并入 WPF 原仓库既有测试工程。
- 本章程中的“单一项目”始终指**一个生产项目**；独立测试项目、原生测试 caller/harness 和文档/基线工件不计入生产项目数量。
- 新项目应尽量隔离 WPF 仓库的全局构建属性、包版本、目标框架和生成流程，避免被现有大型仓库意外影响。
- 新项目不得反向修改原 wpfgfx 源码来掩盖新实现缺陷。
- 在项目骨架和最小导出闭环通过验证之前，不开始大规模源文件翻译。

## 6. DirectX 与 Silk.NET 原则

- DirectX 底层互操作优先评估本地仓库 `D:/lindexi/Code/OriginWpf/Silk.NET`。
- 本地 Silk.NET 是 DirectX 绑定的首选证据与复用来源，但不是可以绕过 ABI、调用约定和 Native AOT 验证的强制黑盒依赖；采用整体项目引用、冻结生成源码或局部手写互操作，必须由专题 spike 的证据决定。
- 使用 Silk.NET 的前提是其接口能够保持原有调用语义、COM 生命周期、结构布局和错误处理。
- Silk.NET 只作为低层互操作工具，不得借机把原 wpfgfx 算法改写成另一套高层渲染架构。
- 对 Silk.NET 未覆盖、版本不匹配或语义不透明的接口，可采用局部手写互操作；该决定必须有专题记录和测试。
- D3D9、D3DEx、DWrite、WIC、DXGI、DWM、GDI、COM 和相关 Windows API 必须分别盘点，不能将“DirectX”视为单一依赖。

## 7. 测试优先级与增量门禁

测试应随迁移逐步增加，不等待全部翻译完成后再补：

1. ABI/布局测试：导出名、调用约定、参数、结构体尺寸、偏移、枚举值和 HRESULT。
2. 纯逻辑单元测试：数学、几何、颜色、像素、区域、命令解析和状态转换。
3. 原生实现与 C# 实现的差分测试：同输入、同状态、同输出或同副作用。
4. 资源与失败路径测试：引用计数、释放顺序、异常封锁、设备丢失、无效参数和低资源情形。
5. 组件集成测试：命令通道、资源创建、软件渲染、硬件渲染和呈现链路。
6. 端到端流程测试：由真实或最小化 PresentationCore 调用路径进入导出库并完成可观察渲染结果。

每个迁移批次必须先定义验收证据，再开始翻译。没有测试或差分证据的“已翻译”只能标记为“代码草拟”，不得标记为完成。

端到端验证不得全部推迟到最后一批。随着真实实现落位，必须按能力逐步扩展：Native AOT probe、版本/工厂、connection/channel、资源命令、软件像素、真实 PresentationCore `RenderTargetBitmap`、硬件/HWND、D3DImage、媒体和关闭/卸载。后续能力未就绪不影响前级测试存在，但不得用前级通过替代后级验收。

## 8. 规划轮次工具禁令与后续执行方式

生成本章程和总体计划的规划轮次及其分派任务中：

- **禁止调用任何命令行、终端或脚本。**
- 禁止 PowerShell、cmd、bash、Python、批处理、构建脚本、枚举脚本以及通过命令执行的间接替代方式。
- 禁止为了方便统计、搜索、构建、测试或生成文档而绕过此限制。
- 只允许使用 IDE 提供的解决方案/项目结构读取、文件搜索、代码搜索、符号导航、文件读取和文件写入能力。
- 因此本轮结论必须区分“静态调查已确认”和“尚待构建/运行验证”；不得把未运行的结果描述为已验证。

每个子智能体的任务说明必须原文或等价地包含上述禁令，并要求其把过程结论及时写入指定专题文档，而不是只在最终回复中汇报。

后续实现轮次不自动继承“禁止构建/测试”的限制。应优先使用 IDE 的项目编辑、构建和测试能力；若需要终端或脚本，必须遵守当轮用户要求和环境授权。无论使用何种工具，都不得跳过可重复的 build/publish/test 证据。

每轮结束前必须更新该文件，至少包含：

## 11. 逐文件迁移台账状态

后续每个原生文件至少使用以下状态之一：

- `NotInvestigated`：尚未调查。
- `Investigated`：依赖、职责和测试点已记录。
- `Blocked`：存在前置依赖或技术阻塞。
- `Scaffolded`：仅有 C# 类型/签名骨架。
- `Translated`：已完成近似直译，但验证未完成。
- `UnitVerified`：纯逻辑或局部行为已验证。
- `DifferentialVerified`：与原实现差分验证通过。
- `Integrated`：已进入组件链路。
- `EndToEndVerified`：真实端到端链路通过。
- `Accepted`：满足该文件全部迁移完成条件。

不得跳过中间证据直接标记为 `Accepted`。

## 12. 变更与例外管理

- 本章程的强约束只能由用户明确修改。
- 若调查发现某条原则技术上不可行，应先记录证据和影响，不得自行绕开。
- 任何例外都必须写入总体计划和当前交接文档，并注明适用范围；局部例外不得扩展为普遍规则。
- 重构和优化必须在等价迁移完成后另立计划、另设测试基线，不与翻译提交混合。

## 13. 首版规划交付轮次边界（历史记录）

生成首版调查和总体计划的规划轮次只完成：

- 静态探索；
- 专题调查文档；
- 总体迁移计划；
- 后续会话分派和交接文档。

该规划轮次明确不完成：

- 创建生产项目或测试项目；
- 编写 Native AOT 导出原型；
- 翻译任何 wpfgfx 生产实现；
- 修改现有 WPF/wpfgfx 项目；
- 构建、运行测试或枚举实际二进制导出。

上述实现工作从后续轮次开始，并须严格遵守本章程。当前真正可领取的工作以 `next-session-handoff.md` 为准，不得用本历史边界阻止已明确分派的后续实施。
