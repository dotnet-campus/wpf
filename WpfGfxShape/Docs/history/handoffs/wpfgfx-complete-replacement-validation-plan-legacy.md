## 1. 任务与最终目标

本轮任务不是只增加测试、整理文档或取得局部通过，而是：**实现并验证 WpfGfxShape 能够完整替换原来的 wpfgfx.dll**。子智能体必须发现差异、定位根因、修复生产实现并重新验证，直到满足本文的完成条件；存在未闭关键缺口时只能报告未完成。

完整替换的验收边界为 Windows x86 Release、x64 Release，使用真实 WPF 调用方和官方同版同架构模块独立对照。DLL 进程驻留，DLL 卸载及 ARM64 不在范围。没有固定 runtime 合同；每次必须记录实际 .NET/WPF/官方模块版本，不能以单个 servicing 版本的成功证明所有版本兼容，也不能擅自把产品限制到当前测试版本。

有限测试不能数学证明任意未来版本、任意输入都等价。完整替换必须有明确支持范围、覆盖闭包和可追溯证据；不能用这项限制降低实现目标，也不能承诺未验证范围已经兼容。

## 2. 用户确认的约束（覆盖历史冲突条款）

1. 正式配置只有 **x86 Release 和 x64 Release**。不要求 Debug 矩阵，也不按上层 WPF 应用的 Debug/Release 重复设门。
2. 测试驱动、夹具、ABI 探针、比较器及报告逻辑必须完全采用 **C#/.NET**。禁止新增 C/C++ 辅助 DLL、原生探针、汇编或原生代码生成方案。C# 调用官方 DLL、候选 DLL 和必要的系统接口属于允许的被测调用，不是原生测试实现。
3. 五项关键维度：二进制兼容、功能结果、时序行为、资源行为、恢复能力（重点 device-loss、resize）。
4. 错误行为只处理错误输入。不把环境问题的错误码、异常或失败细节等价设为验收门；环境变化用于触发 device-loss 时，验证的是恢复能力。
5. 性能、额外原生 hardening 等非关键项目不单独设为完成门槛。卡死、无限等待、资源无限增长、恢复失败仍属于五项关键维度的问题，不能借此排除。
6. 仅使用 WpfGfxShape.Tests 与 WpfGfxShape.ComAcceptance 两个正式项目。需要隔离时使用现有 exe 的不同角色，不增加第三 Host 或 eng 工程。
7. 保留真实官方零阈值差分，不改 golden、阈值或 skip 来消除差异；不以软件 fallback 冒充硬件路径通过。
8. 本任务允许在上述两个项目增加、修改必要测试，并修复生产实现。旧文档中“本轮不新增测试/不扩项”只描述已完成的历史轮次，不限制本任务。

## 3. 五项验收内容

| 维度 | 必须验证 | 主要证据 |
|---|---|---|
| 二进制兼容 | 加载和导出、调用约定、参数和结构布局、COM/vtable/对象身份、引用和回调合同；真实调用方正确交换数据 | 纯 C# 独立 ABI 夹具、官方/候选调用结果、重复调用及后续状态 |
| 功能结果 | 几何、stroke、brush、clip、mask、图像、glyph、shader、多输入、格式、媒体等适用路径，以及组合输入 | 原始数值/像素、非空及内容更新断言、零阈值独立差分 |
| 时序行为 | 提交与完成、资源更新、回调、重入、注销、关闭及在途任务的必要先后关系 | 事件轨迹、完成条件、有界等待、丢失/重复/关闭后回调检查 |
| 资源行为 | 对象、COM 引用、线程、callback、队列、CPU/GPU 资源在成功、关闭和恢复后收敛 | 引用/生命周期记录、循环统计、预热后趋势、官方对照 |
| 恢复能力 | resize、实际 device-loss 及恢复后更新与绘制；旧 device/surface/cache 正确失效 | 触发确认、恢复事件、新帧内容、连续恢复及最终释放证据 |

错误输入使用有界独立用例，检查适用合同和安全后果；不扩展为任意无效指针或所有环境错误的行为复制。对现有失败不得随意删除测试；区分真实关键缺陷、错误输入、范围外环境错误，并保留理由和原始证据。

## 4. 官方/候选差分框架

- 同一场景描述分别交给官方进程和候选进程；官方不得经候选实现转发，比较器不复用候选算法生成预期。
- 身份取自实际进程和模块，而不是预期文件路径：架构、指针宽度、模块完整路径/SHA、.NET/WPF 版本及官方来源。记录产物与源码修订或变更清单。
- 每个场景保存参数、随机 seed（如有）、原始输出、关键状态及事件、实际 backend、比较结果、超时/崩溃和资源观测。
- 保留 HRESULT 等诊断信息，但环境 HRESULT 一致不是正式门。
- 必须有独立内容断言：预期对象确实绘制、提交的新帧确实可见；不能两边空白或旧帧相等就通过。
- HW 场景确认真实设备、adapter/backend 和实际内容消费链；没有进入目标路径就记未覆盖，不能记通过。
- 时序比较必要偏序和完成条件，不要求两进程墙钟时间或无关事件全序完全相同。
- 如出现官方自身不稳定，先做官方对官方重复对照并定位来源；不直接放宽候选阈值。

## 5. 纯 C# ABI 验证

测试侧独立编写结构及调用声明，不引用候选 ABI 类型作为唯一预期。可使用 sizeof、Unsafe.SizeOf、Marshal.OffsetOf、原始缓冲区及适用的 unmanaged function pointer 等 .NET 能力。

布局自洽只是辅助证据。必须将可区分的字段值交给官方和候选执行相同调用，核对结果、回调及后续对象状态。覆盖指针宽度、内部自然对齐与公开 packed 参数、C++ 成员调用与 COM/自有函数表之间的真实区别，避免再次混淆这些合同。

覆盖连续调用、复杂参数、资源释放、COM 身份/引用、合法缓冲区边界哨兵和回调；高风险用例在现有 exe 隔离角色执行。缓冲区哨兵不能证明所有读越界不存在。

纯 C# 无法直接可靠观测的 ESP/寄存器细节不得声称已直接验证，也不得生成机器码或引入原生探针补齐。使用重复调用、后续操作和状态检查发现其外部后果，并如实写明证据边界；直接 ESP 探针不是本任务门槛。

## 6. 场景与序列

### 6.1 基础状态序列

创建 → 首帧 → 更新资源 → 再绘制 → resize → 再绘制 → 释放。

对各关键节点验证内容及生命周期；更新时使用显著不同的帧，防止旧内容假通过。覆盖反复 resize、可支持的最小尺寸、非整数变换、多 target、多窗口及资源共享等合法组合。

### 6.2 恢复序列

正常绘制 → 确认 device-loss 已发生 → 恢复 → 更新为新内容 → 验证新帧 → 再恢复/resize → 释放。

子智能体先调查现有 C#/.NET 可用触发机制，选择能够证明实际发生的路径。纯模拟状态变化只能作为补充，不能冒充真实恢复证据。没有可用真实 HW 或触发条件时记为阻塞/未覆盖，并提交所需条件，不能宣布完整替换。

检查 cache generation/per-device 失效、D3DImage/device/surface 引用、关闭与在途回调竞争。环境错误码是否相同不影响判定；恢复内容、时序及资源是否正确影响判定。

### 6.3 渲染组合与真实 WPF

按现有源码和测试盘点真实 producer/consumer 路径，覆盖几何、stroke/dash、transform/clip、opacity/mask、brush、采样、glyph、shader/多 sampler、FLOAT/HDR、媒体的适用组合。格式支持必须有实际内容证据。

通过真实 WPF 调用方提交窗口绘制、动画/布局更新、滚动、多窗口、多 UI 线程、RenderTargetBitmap、D3DImage 和持续媒体等场景。直接底层测试与真实调用方 E2E 互补，不能相互代替。

### 6.4 时序和资源循环

重复创建、更新、绘制、恢复和关闭。检查丢失/重复回调、关闭后访问、卡死、未完成任务及残留线程。等待有明确超时并收敛任务；具体循环数、预热次数及超时先按现有框架和官方观测确定，写入场景，不在失败后随意修改。

区分合理缓存与泄漏：检查预热后是否稳定，而不是要求每次释放立即回到初始内存。保留样本序列和官方对照；不能只给最终一次内存值。DLL 驻留不免除对象及资源清理。

## 7. 未知差异发现与测试有效性

在固定回归完成后增加合法渲染图和合法操作序列的约束随机差分。固定并保存 seed；失败时缩减节点、路径段、数值和操作序列，形成稳定最小回归用例。随机测试用于发现缺陷，不重复运行到偶然成功来覆盖失败。

增加纯 C# 负控验证，例如给比较器输入错误颜色/旧帧，给生命周期检查器输入缺失释放/重复回调轨迹，确认会失败。对测试副本可控地注入场景错误时，不更改正式候选或官方对照。负控只证明对应检测环节有效，不能把它冒充完整生产路径缺陷注入证据。

## 8. 子智能体执行顺序

1. 阅读交接入口、执行规则、当前基线和本文；检查仓库指令及两个正式项目结构，盘点五维覆盖与现有测试，不恢复历史治理门。
2. 确认当前源码和产物身份；准备 x86/x64 Release 正式验收包，建立当前候选完整现有回归基线。保留失败、超时和未覆盖，不拼接旧 SHA 结果。
3. 重新裁决历史 32 项 HW 失败及相关未闭路径，逐项确认是否真实执行目标 backend/内容，按本文范围分类。
4. 补齐独立纯 C# ABI 夹具及实际调用证据，修复生产根因并回归受影响路径。
5. 实现组合内容差分与真实 WPF E2E，确认非空、新内容和真实 producer/consumer 闭包。
6. 实现时序、资源、resize 和真实 device-loss 恢复序列，覆盖持续媒体及关闭竞争。
7. 执行约束随机差分、失败缩减、负控及循环资源验证；为发现的每个实际缺陷增加稳定回归并修复。
8. 最后源码修改后重新发布必要产物，运行最终 x86/x64 Release 完整适用矩阵；回读实际 identity、TRX、业务 JSON、图像和事件/资源原始数据，再更新交接和结论。

可以按有界包分配子智能体，但修改共享实现或测试基础设施时必须协调。每个子智能体交付文件清单、根因、测试命令对应的专用工具记录、实际结果、证据路径和未闭项；不能只交付文档或构建成功。主执行者负责最终集成与两架构全量验收。

## 9. 完成与失败裁决

维护“关键能力/调用路径 × x86 Release/x64 Release × 五维”的矩阵，条目必须链接具体测试与原始证据。标记通过、失败、未覆盖、阻塞或有依据的不适用；不适用不能用于排除本应支持的功能。

- 官方成功、候选失败：优先认定候选缺陷并定位。
- 双方成功但内容、必要时序、资源或恢复不同：差异未闭。
- 双方失败：不能直接算通过，调查共同前置条件与测试链路。
- 目标 HW/恢复路径未实际触发：未覆盖。
- 仅环境错误码不同，且不影响关键行为：记录，不单独阻塞。

宣布能够完整替换必须同时满足：两架构 Release 的全部适用关键能力有证据、真实调用方闭包成立、无未解释关键差异、无关键未覆盖/阻塞、资源和恢复收敛、最终结果绑定最后源码对应的实际产物。仍有关键缺口就继续修复或明确报告未完成，不按通过率关门。

额外 hardening 范围未知应如实披露，但不单独阻塞本任务；若发现有效输入或关键行为受影响，则按实际缺陷处理。retail 已 Closed；私有 PRERELEASE player 非目标，不重新设门。
